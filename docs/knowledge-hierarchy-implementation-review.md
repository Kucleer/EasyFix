## 2. 必须修正的问题

### R1 [P1] 维护保护只检查请求入口，无法保证最终备份后不再落入在途写入

**位置**：`cloudflare/src/auth.py:56`、`cloudflare/src/questions.py:166` 附近的 batch 写入；`cloudflare/src/knowledge.py` 的 `save_directory`；`cloudflare/src/media.py:84`。

guard 读取维护状态后就进入业务处理，业务写入事务没有再断言维护状态。音频请求也在外部 fetch 前检查一次，fetch 返回后直接写 R2。全局搜索 `write_maintenance` 未发现数据库事务或触发器层门禁。

**触发场景**：

1. 请求 A 在维护关闭时通过 guard，随后等待公式校验、模型、数据库读取或音频回源。
2. 运维打开维护并开始最终快照/回填。
3. 请求 A 恢复执行，仍能提交 D1 写入或 R2 缓存。

在内存库中设置 `write_maintenance=1` 后直接调用 `save_directory` 仍成功，证明服务本身没有第二层保护。该复现不是 HTTP 绕过认证，而是模拟已越过入口检查的请求继续执行；真实长请求竞态尚需隔离环境验证。

**影响**：备份基线与回填期间的数据可能继续变化，违反最终方案第 12.1 节。实施手册仅写“排空在途任务”，没有可执行的活动任务观测或排空完成判定。

**修正建议**：

- 将 D1 业务写入门禁放到相同事务中，或采用等效数据库保护，覆盖普通内容编辑、目录、批改、报告等全部写入路径。
- 为迁移建立受控通道，不能增加所有 Bearer 都可用的维护绕过。
- 对 R2/外部生成副作用提供排空机制与可验证的完成标准；音频回源结束后也需处理维护状态变化。
- 发布 A 的代码清单、构建产物及实际验证方式单独固定，不能只把已含新 schema 依赖的完整实现当维护版本部署。

**回归要求**：暂停一条已经通过 guard 的请求，打开维护，再恢复请求；确认事务拒绝落库、外部副作用受控，且可以证明排空后再取最终快照。

### R2 [P1] 回填末尾只检查主考点数量，缺失次要考点会静默成功

**位置**：`cloudflare/scripts/knowledge_backfill.py:180`、`:194`、`:209`。

`question_sql` 使用 `INSERT … SELECT … FROM knowledge_point WHERE code=... AND deleted=0`：目标编码不存在时插入 0 行，不会失败。`assertion_sql` 只检查“有任意关联时恰好一个主考点”，没有校验实际关联集合是否等于审核映射。

**已复现**：审核目标为 `codes=['MISSING','PRIMARY']`，主考点为 `PRIMARY`；库中仅存在 PRIMARY。执行生成器的 guard、question_sql、structure 后成功，仅留下 PRIMARY。脚本还递增了题目版本。

**影响**：目录 SQL 漏执行、目标被软删除或环境与生成快照不一致时，已审核次要考点可以丢失；若全部目标不存在，空关联也满足当前结构断言。当前通用一致性检查只能证明已存在的数据结构合法，不能证明审核清单完整落库。

**修正建议**：

- 批次首条在数据库内确认全部目标 code 存在、有效、为同科二级，并确认目标主考点属于集合。
- 批次末尾对审核集合与实际有效关联做双向差集检查，并比较主考点，不只比较数量。
- 缺任何目标必须整批失败，不能依赖生成时快照校验。
- 每批回读同时与 manifest 的题目、编码和主考点映射核对；一致性脚本零违规不能替代映射一致性检查。

**回归要求**：缺次考点、缺全部考点、目标软删除、额外多出关联四种情况均整批回滚，题目版本及旧关联不变。

### R3 [P2] 时间窗口的复习覆盖率分子分母不是同一题目集合

**位置**：`cloudflare/src/knowledge_stats.py:53`、`:55`、`:102`、`:144`。

题数按 `q.created_at` 过滤，但 `reviewed_question_count` 使用练习正确率查询，只按练习批改时间过滤，随后直接除以过滤后的题数。

**已复现**：同模块两道题，一道在收录窗口外、一道在窗口内，两题均在练习窗口内被批改。结果：题数 1、已复习题数 2、覆盖率 200%。复现使用固定旧/未来日期，使测试不依赖运行当天；实际数据只需“上月旧题本月复习”即可触发同样问题。

**修正建议**：将覆盖率聚合从正确率查询中拆出：覆盖率分母是收录筛选集合，分子必须是该集合内有符合定义的有效作答的题目。模块练习正确率仍按批改时间包含旧题，不应为修覆盖率错误而给整个正确率查询加收录时间条件。明确覆盖率要求“曾复习”还是“窗口内复习”，并在报告口径中记录。

**回归要求**：覆盖率始终在 0–100%；旧题本期作答仍进入模块正确率，但不放大本期收录题的覆盖率。

### R4 [P2] 练习批改的数据库版本冲突会变为 500，而不是约定的 409

**位置**：`cloudflare/src/practices.py:193`、`:236`；`cloudflare/src/auth.py:68` 附近异常处理。

`knowledge_review_statements` 把客户端版本放入数据库 guard，批改最终直接 `await db.batch(statements)`，没有像 `questions.py` 那样捕获并使用 `map_error`。版本过期时触发器抛 `KP_GUARD`，异常会被 auth 通用异常处理转换为 500。

**触发场景**：用户打开批改页面后，另一入口调整了同题分类；用户再提交批改中的分类修改。

**影响**：用户看到“云端处理失败”，无法按 409 的刷新流程解决；同路径的结构/引用触发器错误也缺少明确的 422/409 映射。该结论来自调用链审查，本轮未新增该接口的 HTTP 竞态测试。

**修正建议**：批改 batch 复用统一 D1 错误映射，保留事务回滚；未知故障仍为 500，不把全部异常吞成 409。

**回归要求**：调用 `/api/practice-sets/{id}/mark-reviewed` 提交过期分类版本，HTTP 返回 409，批改、分类、计数器均不发生部分写入；结构校验返回 422。

### R5 [P2] 删除原主考点后仍有多个考点时，选择器会静默指定新主考点

**位置**：`frontend/src/components/KnowledgePointPicker.vue:99`。

当原主考点被移除，且剩余二级数量大于 1 时，代码直接 `primary.value = selected.value[0]`。这与方案“多选时让用户明确选择主考点”不一致；主考点决定模块占比，不只是视觉排序。

**触发场景**：选择 A、B、C，A 为主考点；取消 A，B、C 来自不同一级。系统自动将 B 作为主考点，用户不需要确认即可保存并改变统计归属。

**修正建议**：剩余单项可自动指定；剩余多项且原主考点失效时设为 null，展示已有提示并阻止提交，直到用户明确选择。

**回归要求**：单选自动指定；保留原主考点时不变；多选移除主考点后需要重新选择；Upload、Questions、PracticeSets 三个入口行为一致。

## 3. 其他需对齐的事项

以下不计入上述 5 个独立缺陷，但应在修订实施说明时说明：

- 实施说明称 `cache.py` 已改动，但已知边界又称其未改动；文件清单应按实际 diff 描述“复用现有机制”。
- `knowledge.py` 头部注释写“0081 迁移”，实际迁移为 0009，应纠正。
- `knowledge_stats.py:157` 的 `parent_share_percent` 把兄弟二级的计数相加后算一个比例，再给每个子项赋相同值；这不是单个二级在父级内的占比。若本期不消费该字段，建议移除；如保留，先定义分母及多标签去重口径并补测试。
- 回填工具声称幂等，但成功批次已经递增知识版本，直接重放同一文件会 guard 失败。这可以作为安全防重策略，但手册应区分“可安全重试未提交批次”与“已提交批次可重复成功”，给出依据 manifest 与回读结果判断是否跳过的明确步骤。
- 生产前仍需目录种子、逐题映射、Agent 提示词审核，以及发布 A/B、备份恢复和实际 D1 行为演练；现有本地测试不代替这些证据。

## 4. 修正后的放行标准

1. 修复 R1–R5，并将对应复现条件加入自动化或明确的交互验证。
2. 18 项不变量与 6 项 HTTP 集成测试继续通过，新增批改冲突、维护在途写入、回填集合完整性用例。
3. 增加时间窗口覆盖率边界测试，验证正确率与覆盖率分开计算。
4. 构建并浏览器检查共享 Picker 的三个实际入口；本报告未重新构建，不能把报告作为前端验收证据。
5. 在隔离 D1 演练事务失败回滚、触发器错误映射与迁移恢复；实际运行限制及平台恢复能力按实施时官方资料核对。
6. 更新实施说明，准确区分“已实现”“已本地验证”“待隔离验证”“待生产验证”。

修复后做聚焦复审。当前结论不否定已有两级模型、原子分类替换和一级聚合的主体实现，但现有证据不足以支持直接执行生产迁移。
