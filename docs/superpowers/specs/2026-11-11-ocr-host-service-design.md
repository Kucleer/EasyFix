# 主机端开发与配置：EasyFix 识别服务

日期：2026-11-11
状态：已确认（2026-11-11）
读者：在那台装了 OCR 模型的 Windows 主机上做开发和配置的人（或助手）。这份文档可以单独看，不需要先读别的。
配套文档：`2026-11-11-page-scan-intake-design.md`（整体方案，云端和页面部分）、仓库根目录的 `ocr-ollama-handoff.md`（这台主机上的 OCR 实测与交接）

文中 **【用户定】** 是用户明确说的，**【Claude 定】** 是 Claude 替用户选的，可以改。

## 1. 背景

EasyFix 是学生错题整理应用，正式环境在 Cloudflare（后端是 Python Worker，数据在 D1，照片在私有 R2），入口 https://easyfix-bl2.pages.dev 。

现在要加一条录题的路：孩子妈妈在网页上传一张整页作业照片，系统识别后把做错的题预填出来，她核对后入库。识别分两段：

1. **读图**：把照片变成文字。用这台主机上已经跑通的本地 OCR 模型。**这是主机端的事。**
2. **整理**：把文字拆成题、判断对错、补答案和考点。由云端后端调用文本模型完成。这不是主机端的事。

云端后端通过 Cloudflare 的 Workers VPC 隧道调用这台主机。主机不对公网开任何入口。**【用户定：走隧道，不买域名】**

## 2. 主机端要交付什么

| # | 交付物 | 说明 |
| --- | --- | --- |
| 1 | 识别服务 | 一个只监听本机的小 HTTP 服务，收一张图，调本机 Ollama，返回文字。接口见第 4 节，**必须严格按约定做**，云端按同一份约定开发 |
| 2 | 强化重扫 | 识别服务的第二种模式，用回归图调出一个有效的做法。见第 5 节 |
| 3 | 开机自启 | Ollama、识别服务、隧道客户端重启后自己恢复。见第 6 节 |
| 4 | 隧道 | 安装 `cloudflared`，连上用户 Cloudflare 账号里的隧道，登记 VPC 服务。见第 7 节 |
| 5 | 安装说明 | `tools/easyfix-ocr-host/README.md`，面向初学者，一步一条命令 |
| 6 | 回传给云端的信息 | 见第 9 节 |

### 不属于主机端的事

- 拆题、判断对错、打考点、调用文本模型。
- 网页、数据库、Cloudflare Worker 的代码。
- 换模型、调模型参数、重新做 OCR 准确率评测。交接文档里的实测数据直接采用。**【用户定】**

## 3. 这台主机的现状（来自交接文档）

- Windows PC，RTX 4070 Ti 12GB，平时常开。
- 便携版 Ollama 0.40.16，模型 `longwayxu/xiaomi-ocr-0:bf16`，监听 `127.0.0.1:11435`。
- 启动脚本：仓库根目录下 `tmp/xiaomi-ocr/ollama/start.ps1`。
- Python 环境：`tmp/xiaomi-ocr/.venv`，已有 Pillow 和 httpx。
- 官方适配代码 `official_backend.py` 在 `tmp/xiaomi-ocr/` 下，包含图片预处理和非思考提示词。实测就是用它跑的。
- 回归材料：`tmp/xiaomi-ocr/regression/report.md`（20 张图、61 道目标题的逐题评分）、`tmp/xiaomi-ocr/sign-test/`（指定题验证）。
- `tmp/` 整个目录被 Git 忽略。

实测结果：整页读图中位 5.2 秒；61 道目标题里 41 道关键题干完全正确，6 道有关键错误；已知读错类型是分母 13 读成 131、负号丢失、手写演算串题、图形条件遗漏。

开工前先确认上面这些路径和版本在主机上确实如此，有出入的地方记下来，按实际情况做。

## 4. 识别服务的接口约定

这一节是主机端和云端之间的约定。两边分开开发，任何一边想改这里的内容，都要先告诉用户，两边一起改。

### 4.1 基本要求

- 只监听 `127.0.0.1`，端口 `11436`。不监听 `0.0.0.0`，不开防火墙入站规则。
- 只用 HTTP，不需要 HTTPS（隧道负责加密）。
- 所有接口都要校验口令：请求头 `X-EasyFix-OCR-Key` 的值必须和配置里的口令完全一致，比较时用防计时攻击的比较函数。不带或不对，返回 401。
- 所有响应都是 JSON，UTF-8。
- 约定版本号是 `1`，每个成功响应里都带 `"contract": 1`。以后约定有不兼容的改动就加一。

### 4.2 `GET /health`

用途：云端判断识别服务能不能用。必须快，2 秒内返回，不触发模型推理。

成功（200）：

```json
{"ok": true, "contract": 1, "ollama": true, "model": "longwayxu/xiaomi-ocr-0:bf16"}
```

- `ollama`：这一刻能不能连上本机 Ollama 并且模型在它的模型列表里。连不上时仍然返回 200，`ok` 为 `false`，`ollama` 为 `false`，其余字段照常返回。
- **不管 `ok` 是真是假，响应里都必须带 `"contract": 1`。** 云端靠它区分"版本不一致"和"Ollama 没起来"。

### 4.3 `POST /ocr`

用途：识别一张图。

请求：

- 查询参数 `mode`：`normal`（默认）或 `enhanced`。其他值返回 400。
- 请求头 `Content-Type`：`image/jpeg`、`image/png` 或 `image/webp`。`image/jpg` 当作 `image/jpeg` 接受。其他返回 415。以图片实际内容为准：声明的类型和内容不符、但内容是这三种之一的，照常处理。
- 请求体：图片的原始字节，不是表单，不是 base64。上限 10MB，超过返回 413。

成功（200）：

```json
{
  "ok": true,
  "contract": 1,
  "mode": "normal",
  "text": "整页的文字，按阅读顺序",
  "segments": ["……"],
  "elapsed_ms": 5234,
  "model": "longwayxu/xiaomi-ocr-0:bf16"
}
```

- `text`：整页文字。`normal` 模式下就是模型的输出；`enhanced` 模式下是各段按顺序拼起来的结果。
- `segments`：`normal` 模式下是只有一项的数组（和 `text` 相同）；`enhanced` 模式下是每一条的文字，按从上到下的顺序。云端可能只用 `text`，也可能两个都用。
- 文字原样返回，不做纠错、不翻译、不加说明。公式保持模型输出的写法。

失败：

```json
{"ok": false, "contract": 1, "code": "ocr_failed", "detail": "给人看的一句中文说明"}
```

| 状态码 | `code` | 什么时候 |
| --- | --- | --- |
| 400 | `bad_request` | `mode` 不认识、请求体为空 |
| 401 | `unauthorized` | 口令不带或不对 |
| 413 | `too_large` | 图片超过 10MB |
| 415 | `unsupported_type` | 不是 jpg / png / webp，或者内容打不开 |
| 503 | `busy` | 排队的请求已满，或排队等了太久（见 4.4） |
| 502 | `ocr_failed` | Ollama 连不上、模型报错、返回空内容 |
| 504 | `timeout` | 这张图处理超过时限（见 4.4） |

`detail` 里不要带图片内容、文件路径、口令或堆栈。

### 4.4 排队和时限

- 显卡一次只跑一张图。同时来多个请求时排队，按到达顺序处理。
- 最多排 2 个（不含正在处理的那个），再多的直接返回 503 `busy`。
- 排队等待最多 20 秒，等不到就返回 503 `busy`。
- 处理时限从开始处理算起：`normal` 模式 45 秒，`enhanced` 模式 90 秒。超时返回 504 并放弃这张图，后面排队的请求照常处理。
- `elapsed_ms` 只报处理用时，不含排队。
- 这样一个请求从到达到返回最多 110 秒。云端按 120 秒等，这几个数字要改必须两边一起改。

### 4.5 配置和口令

- 配置文件：`%USERPROFILE%\.easyfix\ocr-host.json`。至少包含：口令、端口、Ollama 地址、模型名。带 BOM 的文件也要能读（记事本和 PowerShell 存出来的会带）。
- 口令由用户在主机上生成一串足够长的随机字符（不少于 32 个字符），同一串值之后要配到云端后端的密钥里。
- 口令和隧道的连接口令**不进仓库，不写进任何文档、提交说明、日志和对话**。README 里只写"在哪里填"，不写值。

### 4.6 日志

每个请求记一行：时间、模式、图片大小、处理用时、结果（成功或失败的 `code`）。不记图片内容，不记识别出的文字，不保存图片。日志放在 `%USERPROFILE%\.easyfix\logs\`，按天分文件，只留最近 14 天。

### 4.7 读图的做法

`normal` 模式必须和交接文档实测时的做法一致：同样的图片预处理、同样的输入尺寸、同样的非思考提示词（都在 `official_backend.py` 里），不开提示缓存。这样线上效果才和实测数据对得上。不要自己改提示词或尺寸。

唯一允许加的一步是照片方向：手机原片常常是横着存的像素加一个方向标记，云端和网页会把原片原样传过来。两种模式都要在预处理之前先按方向标记把图转正（Pillow 的 `ImageOps.exif_transpose`），保证进模型的图是正的。**【Claude 定】** 开工时先查两件事并写进回传记录：`official_backend.py` 本身有没有做这一步（有就不重复做）；20 张回归图是带方向标记的原片还是已经转正的图。如果回归图本来就是正的，加这一步不会改变实测结果。

## 5. 强化重扫（`enhanced` 模式）

### 5.1 它是干什么的

云端在整理题目时，如果发现文字"看得出不对劲"（公式断了、题解不出、两道题串在一起、缺图形条件），会对同一张图再要一次 `enhanced` 模式的结果，然后把两次的文字一起交给文本模型重新整理。每张图最多要一次，这是兜底，不是常规流程。**【用户定】**

同一张图用同样的设置再读一遍，结果基本不变。所以 `enhanced` 模式必须换一种读法，才可能读出不同的、更准的内容。

### 5.2 起点做法

把整页切成上下几条有重叠的横条，每条单独按 `normal` 模式的预处理和提示词识别，再按顺序放进 `segments`。这样每道题分到的像素更多，而且不需要先知道每道题在图上的位置。**【Claude 定】**

起点参数：切 3 条，相邻两条重叠约 12% 的高度。转正之后仍然宽大于高的图不切，直接放大识别。

### 5.3 用回归图调

用 `tmp/xiaomi-ocr/regression/` 里的 20 张图和逐题评分做靶子：

1. 先找出交接文档说的那 6 道有关键错误的题，记下每道错在哪（哪种读错类型）。
2. 对这些题所在的图跑 `enhanced` 模式，看每道关键错误有没有被读对。
3. 可以调的：切几条、重叠多少、每条是否放大、是否换一个更强调公式和数字的提示词。`normal` 模式的做法不能动。
4. 同时看有没有新的读错：原来读对的题，在 `enhanced` 模式下读错了几道。

要回传的结果（见第 9 节）：6 道关键错误里 `enhanced` 模式救回了几道、分别是哪种类型；原来读对的题里新读错了几道；`enhanced` 模式单张用时的中位数和最大值。

如果怎么调都一道救不回来，不要硬凑。把试过的做法和结果记下来回传，由用户决定是换做法还是去掉重扫。这种情况下 `enhanced` 模式仍然要按第 4 节的约定能调通（返回切条的结果），云端那边由用户决定是否启用。

### 5.4 时间

`enhanced` 模式的目标是单张不超过 30 秒，硬性时限是 4.4 的 90 秒。**【Claude 定】** 超过目标的话优先减少切条数。

## 6. 开机自启

主机平时常开，但重启、断电恢复之后要能自己回到可用状态，不需要有人登录后手工启动。

- Ollama：沿用现有的 `start.ps1`。
- 识别服务：在 Ollama 之后启动；Ollama 还没好时识别服务照常启动，`/health` 返回 `ollama: false`，等 Ollama 好了自动恢复，不需要重启识别服务。
- 隧道客户端 `cloudflared`：装成 Windows 服务。

用什么方式自启（计划任务、Windows 服务）由实施者定，要求是：不需要用户登录桌面也能起来；起不来时在日志里能看出原因；README 里写清楚怎么查看状态、怎么手工停止和启动。

验证：重启主机，不登录，等几分钟，从云端（或按第 8 节的本机办法）调 `/health` 应该返回 `ok: true`。

## 7. 隧道

### 7.1 做什么

用 Cloudflare 的 Workers VPC。在用户的 Cloudflare 账号里有一条隧道，主机上的 `cloudflared` 主动连出去；再在账号里登记一个"VPC 服务"，指向主机上的 `127.0.0.1:11436`；云端后端 Worker 绑定这个 VPC 服务后就能调识别服务。

- 不需要域名，不配公网主机名（Public Hostname）。**不要给隧道加任何公网主机名或路由。**
- 不用临时隧道（`cloudflared tunnel --url ...` 得到的 `trycloudflare.com` 地址）：它只用于测试，重启后地址会变，保护方式程序过不去。
- `cloudflared` 版本不低于 2025.7.0。
- 主机要能向外发 UDP 7844 端口的流量（隧道用 QUIC 协议）。

### 7.2 步骤

Workers VPC 目前是测试版，控制台界面和命令可能和下面的描述有出入，以官方文档为准：https://developers.cloudflare.com/workers-vpc/

1. 在 Cloudflare 控制台的 Workers VPC 里新建一条隧道，得到安装命令和连接口令。**这一步是用户本人操作**，需要账号里有相应的权限（文档里叫 Connectivity Directory Admin）。
2. 在主机上安装 `cloudflared` 并用连接口令装成 Windows 服务。安装包只从 Cloudflare 官方发布页下载。连接口令只留在主机上。
3. 在控制台确认隧道状态是已连接。
4. 新建一个 VPC 服务：选这条隧道，主机填 `127.0.0.1`（或 `localhost`），端口 `11436`，协议 HTTP。得到一个服务编号（service ID）。
5. 把服务编号回传给云端那边（第 9 节）。服务编号不是密钥，可以写进仓库的 Worker 配置里。

从云端 Worker 调通 `/health` 这一步在云端做，不属于主机端。主机端的完成标准是：控制台显示隧道已连接、VPC 服务已建好、本机自测（第 8 节）全部通过。

### 7.3 如果走不通

Workers VPC 在这个账号的免费计划下建不了隧道或 VPC 服务，或者主机网络连不出去：停下来，把看到的报错原样告诉用户。不要自己换成公网主机名、临时隧道或者端口映射。整体方案里留了退路（主机主动向云端领任务），要不要走由用户决定。

## 8. 主机端自测

### 8.1 自动测试

放在 `tools/easyfix-ocr-host/` 下，用 `python -m unittest` 能跑，不需要真的 Ollama 和显卡（用假的 Ollama）：

- 口令不带、不对：401。
- `mode` 不认识：400；请求体为空：400。
- 超过 10MB：413；不是图片或格式不支持：415。
- `normal` 模式成功时的返回结构，字段齐全，`contract` 为 1。
- `enhanced` 模式：切条的数量和重叠符合配置；横拍图不切；`segments` 的顺序是从上到下。
- 排队：同时来多个请求时一次只处理一个；排满之后返回 503；排队超过 20 秒返回 503。
- 带方向标记的图在识别前被转正；`image/jpg` 被接受；`/health` 在 Ollama 连不上时仍带 `contract`。
- 超时：假的 Ollama 一直不返回时，到时限返回 504，后面的请求还能正常处理。
- Ollama 连不上：`/health` 返回 `ok: false`、`ollama: false`；`/ocr` 返回 502。
- 配置文件带 BOM 能读；缺口令时服务拒绝启动并说明原因。

### 8.2 真机验证

在主机上用真的模型：

1. 用回归图里的 3 张，分别调 `normal` 和 `enhanced`，确认能返回文字，`normal` 的文字和实测时的输出一致或基本一致。
2. 连续发 5 张，确认按顺序处理、没有报错、显存没有持续上涨。
3. 完成 5.3 的回归调试并记录结果。
4. 重启主机，按第 6 节验证自启。

验证用的图片和输出只留在被 Git 忽略的目录里，不进仓库。

## 9. 做完后回传给云端的信息

写成一份简短的记录交给用户（可以追加在 `ocr-ollama-handoff.md` 末尾），**不含任何口令**：

1. VPC 服务的服务编号。
2. 识别服务的实际端口和约定版本（如果和本文一致，写"与文档一致"）。
3. 和第 4 节约定有出入的地方（应该没有；有的话必须写清楚）。
4. `normal` 模式单张用时的中位数和最大值。
5. `enhanced` 模式的最终做法（切几条、重叠多少、有没有换提示词）和 5.3 的回归结果。
6. 自启用的是什么方式，怎么查看状态。
7. `official_backend.py` 的来源和许可：能不能随仓库保存（见第 11 节）。
8. 开工时发现主机现状和第 3 节不一致的地方。
9. 照片方向：`official_backend.py` 本身做不做转正，回归图是不是带方向标记的原片（4.7）。

口令（识别服务的共享口令）由用户自己在云端配置时填，不经过任何文档和对话。

## 10. 等云端做完后的联调验收

这一步在主机端和云端都做完之后进行，写在这里是让主机这边提前知道。

云端那边会写好一个验收脚本，由用户带到这台主机上跑。它直接调本机的识别服务和真的文本模型，把 20 张回归图依次走完"读图、整理、需要时重扫"，存下每页的草稿和用时，并生成一张对照表给人工核对。

主机这边要配合的：

- 识别服务处于运行状态，两种模式都可用。
- 脚本只依赖已有的 httpx，不需要装新东西。
- 文本模型的地址和密钥放在本机的配置文件里（具体文件名和字段以验收脚本的说明为准），不进仓库。交接文档里的判错验证（`sign-test/`）已经在这台主机上调过文本模型，沿用同一份配置即可。
- 输出只留在被 Git 忽略的目录里。

另外，云端那边写提示词需要几页真实的识别文字做样本。用户会从这台主机拷几页 `normal` 模式的输出（有 `enhanced` 模式的输出更好）到云端开发用的机器上。这些文字是孩子的作业内容，只放在被 Git 忽略的目录里。

## 11. 代码放哪里

- 识别服务的代码、测试、README、安装和自启脚本放在仓库的 `tools/easyfix-ocr-host/` 下，随仓库管理版本。
- `official_backend.py` 现在在被忽略的 `tmp/xiaomi-ocr/` 里。先确认它的来源和许可：允许随仓库保存就整理进 `tools/easyfix-ocr-host/`；不允许或不确定，就不复制进仓库，改成让识别服务从配置里指定的本机路径加载它，并在 README 里写明要另行获取。
- 在这台主机上开一个分支提交。要不要推送、什么时候合并，问用户。
- 不提交：口令、配置文件、图片、识别输出、日志、`tmp/` 下的任何东西。

## 12. 约束

- 用主机上已有的 Python 环境和依赖（Pillow、httpx）能做完就不加新依赖；确实要加，先告诉用户加什么、为什么。
- 不改 Ollama 的版本、模型、监听地址。
- 不动仓库里 `tools/easyfix-ocr-host/` 以外的代码。云端和页面的改动在另一边做。
- 代码规范和仓库一致：变量小写下划线，函数前写中文文档字符串，复杂逻辑加中文行内注释。
- 用户是编程初学者：README、报错提示都用直白的中文。
- 动系统设置（装服务、建计划任务、装 `cloudflared`）之前，先告诉用户要做什么，得到同意再做。

## 13. 留给实施者决定

- 识别服务用什么写（标准库的 HTTP 服务，或已有依赖），只要满足第 4 节。
- 排队的实现方式。
- `enhanced` 模式的最终参数和是否换提示词（按 5.3 调）。
- 自启用计划任务还是 Windows 服务。
- 配置文件除必填项外的其他字段。
- 任务拆分和先后顺序。建议先做识别服务的 `normal` 模式和隧道，让云端可以尽早联调，再调 `enhanced` 模式。
