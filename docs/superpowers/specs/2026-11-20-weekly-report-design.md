# 每周周报（项目 4）设计

日期：2026-11-20
状态：实施完成，待上线（2026-11-20）
相关文档：`2026-11-10-optimization-roadmap.md`（路线图，项目 4）、`2026-11-11-knowledge-starmap-design.md`（掌握度规则）、`2026-11-12-weekly-paper-design.md`（考点卷、错题毕业）
样稿：`2026-11-20-weekly-report-mockup.html`（用浏览器直接打开；版式、图表类型和文字口吻以它为准）

文中每条决定都标了来源：**【用户定】** 是用户在对话中明确说的；**【Claude 定】** 是 Claude 替用户做的选择，用户审阅时可以改。

## 1. 为什么做

路线图的环是"收集错题 → 整理薄弱 → 针对练习 → 看到提升"。前三步已经上线，最后一步"看到提升"还没有着落。

现有的"学习报告"基本没人用：七个月只生成过 6 份，最近一份是 2026-11-08，全部是旧格式。它要先选条件再手动点"生成"，内容只有模块题数、正确率和几段分析文字，没有和上期的对比，页面上也没有图表。

用户想要的（**【用户定】**）：

- 每周一份学习情况概括：录了多少错题、哪些知识点掌握得不好、单词默写的情况、和近期比有什么提升。
- 多用图表，让数据"好看"，这是坚持下去的动力，**对父母和孩子都是**。
- 配简单的文字总结，**全部站在对孩子说话的角度，多鼓励**；另附一句每期不重样的鼓励。
- 从图上能看出一家人有没有坚持录入错题。
- **周日晚上固定自动生成**，不依赖手动。

## 2. 目标、不做的事、要避免的结果

### 目标

1. 每周日 20:00（北京时间）自动生成一期周报，不需要任何人点按钮。**【用户定：周日晚自动；20:00 是 Claude 定】**
2. 周报是"成长打卡"风格：一句鼓励、几句总结、奖章、打卡日历、考点星星、模块雷达、单词默写、练习卷。**【用户定：选了样稿里的 B 方向】**
3. 所有文字对孩子说（用"你"），鼓励为主。**【用户定】**
4. 图表上的每个数字都由服务端算出，模型只写文字。（沿用路线图原则 2）
5. 生成后的一期不再变化，可以翻看往期。**【Claude 定】**
6. 定时任务失败时能自动补上，不需要人处理。**【Claude 定】**

### 不做的事

- 月报、学期报告。等周报用顺了再说。**【Claude 定，用户未反对】**
- "进行中的本周"实时视图。页面只显示已经生成的各期。**【Claude 定】**
- 回补上线之前更早的周。上线时只补最近结束的那一周。**【Claude 定】**
- 阅读理解。现在只存总正确率，放进来说不出什么。**【Claude 定，用户未反对】**
- 手动生成、手动重写某一期的文字。**【Claude 定】**
- 路线图项目 4 里的这几条本期不做，留在路线图待办：模型"洞察块"、合并两份旧提示词（`prompts.py` 的学习报告提示词和 `analytics.py` 里内联的那份）、补数据缺口（首页错题正确率曲线、阅读按题保存对错）。**【Claude 定】**
- 多学生切换。新表带学生字段，界面不做切换。（沿用路线图原则 5）

### 要避免的结果

- **空夸**：没做到的事也夸，或者每期都是同一句口号。孩子看得出来，很快就没人信。
- 文字里出现"爸爸妈妈帮你录了错题"之类关于父母的话。**【用户定：不要】**
- 文字批评孩子，或者把"薄弱"两个字甩给孩子。
- 文字里的数字、考点名和图表对不上（模型编造）。
- 周日晚上没有生成，而且没人知道。
- 超出 Workers 免费计划。

## 3. 限制

这些是 2026-11-20 查 Cloudflare 官方文档（`developers.cloudflare.com/workers/platform/limits/`、`/workers/configuration/cron-triggers/`）得到的，实施时以当时的文档为准：

- 免费计划有定时任务（Cron Triggers），每个账号最多 5 个。
- 定时任务的每次运行和普通请求一样，CPU 限额 10 毫秒；最长可运行 15 分钟（等待网络不算 CPU）。
- 每次运行最多 50 个子请求，D1 查询和对外的模型请求都算。
- 定时表达式按 UTC 计算；星期用 `sun` 这样的缩写最不容易错（Cloudflare 里 1 是周日）。
- Python Worker 的定时入口写法是 `class Default(WorkerEntrypoint)` 里的 `async def scheduled(self, controller, env, ctx)`。

项目自身的限制：

- 后端每个请求实际都超过 10 毫秒的 CPU 限额（热实例 20–100 毫秒，新实例约 500 毫秒），平台对偶尔超限有宽容，持续超限会中止（2026-11-19 上传 502 的原因）。**所以定时任务的任何一次运行都可能失败，设计必须能重来。**
- 数据库变更只追加迁移，执行前先导出 D1 备份；所有表软删除。
- 掌握度没有历史快照，是读取时按事件现算的（`starmap.load_events` + `mastery_model`）。

## 4. 做法比较

三种做法的区别只在"周日晚上怎么自动跑起来、失败了怎么办"。数据怎么算、页面怎么画，三种都一样。

**方案一：后端自己带定时任务，每次只推进一步。**
在 Python 后端加定时入口，周日 20:00–20:50 每 10 分钟触发一次。每次触发只做一步：第一步算数并保存，第二步写文字。做完了就什么都不做。某一次失败，10 分钟后下一次接着做。打开页面时发现最近一期没做完，页面也会调同一个"推进一步"接口来补做。

- 好处：不新增 Worker，不新增密钥，代码都在后端一处；每步都能重来。
- 代价：要改后端入口（现在是 `Default = asgi.entrypoint(app)`），这个入口承载所有请求，改错了影响全站；需要部署后立刻核对、能马上回滚。

**方案二：单独一个很小的"闹钟"Worker。**
新建一个 JavaScript 小 Worker，只负责周日 20:00 被唤醒，然后通过服务绑定调后端的"推进一步"接口，失败就等一会儿重试。

- 好处：后端入口不用动；JavaScript 几乎不耗 CPU，重试可以在一次运行里完成。
- 代价：多一个要部署和维护的 Worker；它要带一份访问口令才能调后端；出问题时要看两处。

**方案三：不设定时，第一次打开页面时生成。**

- 好处：最简单，不碰入口，不用定时任务。
- 代价：不是"周日晚上固定更新"，周日晚上打开要等几十秒；没人打开就不会有这一期。和用户要的不符。

**选方案一，并把方案三的"打开时补做"作为保底。【Claude 定：用户说的是结果"周日晚自动生成、不依赖手动"，怎么实现交给了 Claude】**
理由：开发者是初学者，少一个 Worker、少一份密钥更好维护；"每次只推进一步"是项目里已有的做法（整页识别的 `/api/scan/pages/{id}/advance`）；入口改动的风险靠"部署后立刻核对、异常马上回滚"控制。

如果实施时发现后端入口无法同时保留现有行为和定时入口，停下来告诉用户，改用方案二，不要自己换方案。

另一个比较过的点：**"上周的掌握度"从哪来。**

- 每期生成时把当时的掌握度存下来，下期拿来比。两套来源（第一期没有上期可比），而且存下来的值和后来补录、重批之后的事实会不一致。
- **每次都按事件现算两个时刻的掌握度（选这个）。【Claude 定】** 只有一条算法路径；一期生成后整份保存，以后不再重算，所以已经生成的各期不会变。哪些事件算"那个时刻已经有了"，见第 5.1 节。已知的小出入：一份卷子后来被重新批改时，系统只认最新一次批改，它的结果会挪到重批的那一周，下一期算出的"上周"可能和上一期当时显示的不完全一样，可以接受。

## 5. 一期周报里有什么

### 5.1 一周怎么算

- 一期的结束时刻 `T_end` 是周日 20:00（北京时间），开始时刻 `T_start = T_end − 7 天`。**【Claude 定，已告知用户："20:00 之后做的事算进下一周"】**
- "本周"是 `[T_start, T_end)`，"上周"是 `[T_start − 7 天, T_start)`。
- **所有数字只用"系统在 `T_end` 之前已经知道"的数据**，这样定时生成和事后补做算出来的一样。"知道的时间"按下表取，**不是**事件在掌握度回放里用的 `at`（错题的 `at` 可能是卷子日期，比录入早）：

  | 数据 | 知道的时间 |
  | --- | --- |
  | 错题 | 录入时间 `question.created_at`（事件里的 `entered`） |
  | 练习卷结果 | 批改时间 `practice_set.last_reviewed_at` |
  | 手动调整掌握度 | `mastery_adjustment.created_at` |
  | 单词默写 | `word_review_log.reviewed_at` |

  算某个时刻 `T` 的掌握度时：先留下"知道的时间早于 `T`"的事件，回放的先后顺序仍按原来的 `at`。这样本周才补录的旧卷子，它带来的变化显示在本周。**【Claude 定】**
- **按条数算的数字**（录入几道、默写几条、正确率、练习卷）用 `[T_start, T_end)`。**按天算的数字**（打卡日历的格子、"默写 N 天"、图注里的"亮了几格"）用这一周周一到周日的自然日，同样只看 `T_end` 之前的记录。这样奖章、文字里的天数和日历上亮的格子一定对得上。上周日 20:00 之后做的事，条数算进本周，格子亮在上周日那一格。**【Claude 定】**
- 页面上显示的日期范围是那一周的周一到周日。
- 2026-11-20 查过正式数据：`question.created_at`、`word_review_log.reviewed_at`、`practice_set.last_reviewed_at` 全部是北京时间、`YYYY-MM-DD HH:MM:SS.ffffff` 这一种写法，可以直接按字符串比较；`paper.paper_date` 只有日期。
- 期数：这个学生已有周报按 `T_end` 从早到晚排的序号，从 1 开始。

### 5.2 从上到下的内容

每块的数字定义如下。数据库里的时间都是北京时间。

**一句鼓励、总结、每张图下面的一句话**：模型写，见第 6 节。

**奖章**（数值为 0 的不显示）：

- 连续 N 周有录入：从本周往前数，连续"至少录入 1 道错题"的周数，最多往前看 26 周。措辞固定为"连续 N 周有录入"，不提是谁录的。**【用户定：不写父母；Claude 定：用中性说法】**
- N 个考点变好：见"考点星星"。
- 默写 N 天：本周有单词默写记录的天数。
- 毕业 N 道：本周毕业的错题数，见"练习卷"。

**打卡日历**：`T_end` 那个周日往前共 42 天，每天两件事：当天有没有录入错题（`question.created_at`，按 `question_scope.counted` 的口径）、当天有没有默写（`word_review_log.reviewed_at`）。三种颜色：只默写、只录入、两样都有。这一块同时回答"一家人有没有坚持录入"，不配评判的文字。**【用户定：要能看出有没有坚持；Claude 定：用日历照实显示】**

**考点星星和各模块**（有两级考点目录的学科各算一份，页面上用"数学 / 英语"切换）：

- 分别算 `T_start` 和 `T_end` 两个时刻每个二级考点的掌握度和档位：用 `starmap.load_events` 读出全部事件，只保留 `at` 早于该时刻的，再用 `mastery_model` 现有的函数算；"学过没有"（`learned_ids`）也用过滤后的事件判断。教材进度和默认年级用当前配置，不追溯。
- 档位从低到高：没学、薄弱、一般、较好、掌握（`mastery_model.status_of`）。
- 环形图：`T_end` 时各档位的二级考点数。颜色和知识星空一致（`frontend/src/composables/knowledgeColors.js`）。
- 变好：两个时刻都学过，档位升高，**并且本周这个考点有做对的练习结果**。变差：两个时刻都学过，档位降低，并且本周这个考点有新录入的错题或做错的练习结果。上个时刻没学、这个时刻是薄弱的，叫"新出现"，不算变差。环形图中间显示变好的个数。
- 只由父母手动调整掌握度引起的档位变化，不算变好也不算变差（环形图和雷达图照实显示调整后的结果）。否则父母点一下，孩子就会被夸"N 个考点变好"，这正是要避免的空夸。**【Claude 定】**（2026-11-20 正式环境里还没有任何手动调整记录。）
- 雷达图：一级模块在两个时刻的掌握度（`upper_mastery`），值为空的模块不画。
- **下一个要攻克的**：`T_end` 时档位是薄弱或一般、并且还有待重做错题的二级考点里，掌握度最低的 1 个（并列时取待重做错题多的，再并列取编号小的）。每个学科最多 1 个，没有就不显示。页面上叫"下一个要攻克的"，不叫"薄弱"。**【Claude 定，已告知用户】**

**单词默写**：本周默写条数、正确数、正确率、有默写的天数；上周同样的数；近 6 周每周的条数。来源 `word_review_log`，**只算默写题型（`review_type=1`）**；选择、听力不算（历史上总共只有 5 条选择题记录）。打卡日历里的"默写了单词"同样只看默写题型。**【Claude 定】**

**练习卷**（错题练习卷，`practice_set.source_type='question'`）：本周批改的份数（`reviewed=1` 且 `last_reviewed_at` 在本周内）、批改题数、做对题数；上周同样的数；本周毕业的错题数。本周没有批改时，这一块只显示一句话。**【Claude 定：用户没提练习卷，Claude 提议加上，用户未反对】**

- 一道题"本周毕业"：`T_end` 时是已毕业、`T_start` 时还不是，**并且本周内这道题有做对的练习结果**。只因为父母"直接设为掌握"而视同毕业的不算。
- 毕业的判断复用 `targeted_model.question_state`（批改结果页显示"刚毕业"用的就是它，取数方式参考 `practices.py` 里它的调用处），题目范围和批改结果页一致，不另写一套规则。两个时刻各算一次，每次只用"知道的时间"早于该时刻的练习结果。

**录入**：本周录入的错题数（分学科）、上周的数。不单独画图，数字供文字和奖章用。

**页面底部**：一个跳到出卷页的普通链接"去出一份考点卷"，一个"旧报告"链接。**【用户定：给父母的操作要弱化，放一个跳转就可以】**

**安静的一周**：本周录入、默写、练习卷都是 0 时照样生成一期，文字照实说、不硬夸，见第 6 节。**【Claude 定，已告知用户】**

## 6. 文字怎么写

每期调一次文本模型（沿用设置页配置的模型，`settings.generate_json`），只给它这一期的数字、考点名和最近 8 期用过的鼓励句，不给题目内容，不给孩子姓名。

模型要写的内容：

| 字段 | 内容 | 长度 |
| --- | --- | --- |
| `cheer` | 一句鼓励，放在页面最显眼的位置 | 不超过 30 字 |
| `summary` | 这一周的总结 | 两三句，不超过 120 字 |
| `captions` | 打卡日历、每个学科的考点块、单词默写、练习卷各一句 | 每句不超过 40 字 |

写作规矩（写进提示词）：

1. 对孩子说话，用"你"。**【用户定】**
2. 鼓励为主，只夸这一周真实做到的事（坚持了几天、哪个考点变好了、毕业了几道题），并且说得具体。**【用户定：多鼓励；Claude 定：只夸真实做到的事，已告知用户】**
3. 不批评。做得不好的地方最多提一处，只用"下一个要攻克的"那个考点，说成接下来一起做的事。
4. 不出现爸爸、妈妈、父母、家长。**【用户定】**
5. `cheer` 必须扣着本周真实发生的一件事，不能是通用口号，也不能和给出的最近 8 期重复。**【用户定：不要每次一样】**
6. 安静的一周照实说（例如"这周歇了一下"），给一个很小的下一步，不硬夸。
7. 数量一律用阿拉伯数字，只能用给出的数字；考点和模块的名字一律放在「」里，只能用给出的名字。

服务端检查（纯函数，不通过就算这次失败）：

- 字段齐全，长度不超。
- 文字里出现的每个阿拉伯数字都在"给模型看过的数字"里。
- 「」里的每个名字都在给出的考点名、模块名里。
- 不含规矩 4 里的词。
- `cheer` 和最近 8 期都不相同。

已知的不足：模型如果把数量写成汉字（"两个"），检查不到。提示词里已经要求用阿拉伯数字。

**兜底文字**：写文字连续失败 3 次（模型请求失败或检查不通过），改用服务端拼出来的文字，记下来源是兜底。兜底的鼓励句从一组事先写好的句子里按期数轮换，同样不和最近 8 期重复；总结和图注用这一期的数字套固定句式。这样即使模型不可用，周日晚上也有一期完整的周报。兜底句子由实施者起草，放在计划里给用户过目。**【Claude 定】**

## 7. 什么时候生成、怎么保证生成

### 7.1 推进一步

一期周报有三个状态：`new`（刚建）→ `facts_ready`（数字算好了）→ `done`（文字也好了）。

"推进一步"是一个函数，定时任务和页面接口共用：

1. 算出目标是哪一期：最近一个已经过去的周日 20:00。
2. 这一期还没有记录就建一条（靠唯一索引防止建出两条）。
3. 状态是 `new`：算数字并保存，改成 `facts_ready`。
4. 状态是 `facts_ready`：写文字（或用兜底）并保存，改成 `done`。
5. 状态是 `done`：什么都不做。

每次调用只做一步。同一步不能被定时任务和页面同时做：用一条带条件的更新来"认领"，做法参考 `scan.py` 的 `claim_step`（记下开始时间，超过一段时间没做完视为卡住，可以被重新认领）。

每一步的 D1 查询要省：算数字那一步控制在 30 条以内，写文字那一步在 6 条以内，离 50 的上限留出余量。

### 7.2 定时任务

- 表达式 `*/10 12 * * sun`（UTC），即北京时间周日 20:00、20:10、…、20:50，共 6 次，只占 1 个定时任务名额。
- 每次触发调一次"推进一步"。顺利的话 20:00 算好数字，20:10 写好文字。
- 维护写开关开着的时候不做任何事。
- 后端入口要同时提供现有的全部 HTTP 行为和新的定时入口。**现有 HTTP 行为必须完全不变**：现有测试全部通过；部署后马上核对 `/health`、一个需要登录的接口、登录页，有异常立刻回滚到上一个 Worker 版本。
- 定时任务里没有请求对象，而 `settings.load`、`generate_json` 等函数现在从请求里取环境。实施者可以传一个只带 `scope={'env': env}` 的替身，不要为此改动现有的调用方。

### 7.3 打开页面时补做

页面打开时，如果最近一期不存在或没到 `done`，页面循环调"推进一步"接口直到完成（有次数上限，中间隔几秒），期间显示"正在准备这一期周报"，并先显示上一期（如果有）。

这同时解决三件事：定时任务 6 次都失败、上线当天还没有任何一期、上线后的第一期（补的是上线前刚结束的那一周）。

已知的不足：如果某一周定时任务全部失败，之后一整周又没人打开页面，那一期会被跳过，不会回头补。可以接受。

### 7.4 看得见失败

现在三个 Worker 都没开历史日志，2026-11-19 查 502 时只能靠实时抓。**给后端打开 Workers Logs**（`cloudflare/wrangler.jsonc` 里 `observability.enabled`），定时任务失败时能查到原因。**【用户定，2026-11-20：需要打开历史日志】**

- 官方文档（2026-11-20 查）写明免费计划包含，每天 20 万条、保留 3 天；同一页提示 2026-12-01 起改用新的计费方式。**打开之前实施者要再核对一次当时的免费额度**，如果已经不在免费范围内，停下来告诉用户，不要打开。
- 只开后端这一个 Worker。日志里不得出现访问口令、会话密钥、模型密钥和模型返回的原文；定时任务每次运行只打印一行：哪一期、做了哪一步、成功还是失败、失败的简短原因。

另外，每一步失败都把简短原因写进这一期的 `error` 列、写文字失败的次数写进 `attempts`，日志过期后还能查到；页面上不显示它们。

## 8. 数据

新迁移 `cloudflare/migrations/0016_weekly_report.sql`，只新建一张表 `weekly_report`：

| 列 | 说明 |
| --- | --- |
| `id` | 主键 |
| `student_id` | 学生，默认 1（路线图原则 5） |
| `week_end` | 这一期的结束时刻 `T_end`（北京时间） |
| `status` | `new` / `facts_ready` / `done` |
| `step_started_at` | 正在做的那一步的开始时间，用于认领 |
| `facts` | 这一期的全部数字，JSON，带 `schema_version` |
| `text` | 这一期的文字，JSON |
| `text_source` | `model` 或 `fallback` |
| `attempts` | 写文字已经失败的次数 |
| `error` | 最近一次失败的简短原因（不含密钥和模型原文） |
| `created_at` / `updated_at` / `deleted` | 沿用现有规范 |

## 9. 接口

| --- | --- |
| `GET /api/weekly-reports` | 各期的简表（编号、期数、日期范围、状态），新的在前 |
